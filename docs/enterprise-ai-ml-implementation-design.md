# 企业内部交互式 ML 自动化实施设计稿

## 1. 实施结论

如果上一份架构文档回答的是“为什么这件事成立、边界应该怎么切”，那么这份实施设计稿要回答的就是“第一版到底怎么做，做到什么程度算落地”。结合当前代码，最合理的第一阶段实现并不是把 `autogluon-assistant` 改造成一个全新的企业平台，也不是把 ACP 直接暴露给前端后让它自己承接所有业务职责，而是在“ACP 轻编排层”和“求解器”之间增加一个轻量的 `ML Session Orchestrator`。这个中间层一头接 ACP 的会话、意图识别、阶段判断和主动控制能力，一头接 `autogluon-assistant` 的任务与迭代求解能力，负责把用户的多轮讨论沉淀成结构化任务，再把求解过程翻译成稳定的会话事件流。

这样设计的好处有两个。第一，改造面足够克制。第一版不需要侵入式重写 `NodeManager` 的求解逻辑，也不需要推翻现有 MCP/WebUI 相关能力，只要在求解器外层把状态机、任务定义和会话桥接补起来，就能把一次性任务执行升级成可讨论、可确认、可执行、可轮间优化的交互式系统。第二，边界足够清楚。ACP 不再只是协议入口，而是承担会话级轻编排、阶段判断和事件入口；`autogluon-assistant` 继续做求解；企业平台自己的 Orchestrator 则收敛到“任务沉淀、状态持久化、执行控制、事件翻译”这类重编排职责，不和底层求解逻辑打架。

第一版的目标不应过大。更务实的目标，是先把三条链路打通：讨论链路能不能进入同一个会话，执行链路能不能真正调起求解，反馈链路能不能把每轮状态稳定映射回 ACP。只要这三条链打通，并且能支持“轮与轮之间插入修改、下一轮生效”，这套方案就已经具备很强的可用性。

### 小结

第一版最重要的不是做大，而是把三层角色切清楚：ACP 负责轻编排与主动控制，Orchestrator 负责重编排与持久化执行控制，`autogluon-assistant` 负责求解。

## 2. 模块拆分

### 2.1 总体模块

建议第一版至少拆成下面五个核心模块：

| 模块 | 作用 | 建议位置 |
|---|---|---|
| ACP Control Gateway | 承接 ACP session、prompt、轻量意图识别、模式切换、配置切换、分支请求与事件订阅 | 新增服务层，依赖 `packages/opencode/src/acp` |
| ML Session Orchestrator | 维护业务会话状态、任务草案、后续约束与执行控制 | 新增 `packages` 或独立服务目录 |
| Task Spec Builder | 把多轮对话整理成结构化 ML 任务定义 | Orchestrator 内部模块 |
| ML Runner Adapter | 把任务定义映射到 `autogluon-assistant` 的执行入口 | 新增适配层 |
| Artifact & State Store | 保存业务会话、运行状态、产物索引和评估摘要 | 业务数据库 + 文件/对象存储 |

这五个模块里，`ML Session Orchestrator` 仍然是第一版的业务核心，但它不再需要吞下全部编排职责。更准确地说，当前这个 session 处于讨论、确认、执行还是继续优化，ACP 其实完全可以先做一轮会话级判断；Orchestrator 更适合承接的是业务上更重的部分，例如任务草案结构化、后续约束持久化、当前运行实例管理和结果索引维护。这样一来，ACP 的主动能力不会被低估，Orchestrator 也不会膨胀成一个什么都做的中台。

### 2.2 Orchestrator 内部建议怎么拆

第一版不建议把 Orchestrator 拆成多个微服务，但建议在代码边界上至少拆成五个子模块：

| 子模块 | 职责 |
|---|---|
| Session Context Manager | 管理业务会话元信息、用户约束、任务草案与当前运行指针 |
| Task Spec Builder | 把 ACP 轻编排层整理出的会话信息沉淀成结构化任务定义 |
| Execution Controller | 决定何时启动、暂停、继续或终止一次求解 |
| Constraint Store | 持久化轮间修正、后续约束与运行期覆盖项 |
| Event Translator | 把求解状态、分数变化和结果摘要翻译成 ACP 会话事件 |

这样的拆法有一个现实好处：会话级输入判断和命令公开尽量前移到 ACP 侧，Orchestrator 则专注于可持久化、可审计、可回放的重编排职责。这样即使第一版先把它们写在同一个服务里，后续也容易在不改外部协议的前提下逐步演进，不会出现“所有判断都堆在一个编排器里”的问题。

### 2.3 `autogluon-assistant` 第一版怎么接

第一版不建议深改 `autogluon-assistant` 内核，而建议尽量从现有入口往外包。当前最稳妥的接法，是保留 `run_agent()` 作为求解入口，在外层准备好输入目录、输出目录、配置、最大迭代数、是否启用轮间输入和初始用户指令，再通过运行状态、日志和输出目录回收结果。这条路径改动最小、接入最快，也最符合“不要过度实现”的原则。

更进一步的接法，是在 `NodeManager.step()` 的前后加轻量事件钩子，让 Orchestrator 可以不用只靠日志判断每轮状态，而是能拿到更明确的“开始新一轮”“当前选中工具链”“执行完成”“分数更新”“最佳结果更新”等信号。不过这一步更适合作为第二阶段演进，而不是第一版硬要求。第一版完全可以先接受较粗粒度的状态流，只要会话、执行和轮间修正先跑顺，价值就已经成立。

### 小结

模块设计的重点不是拆得越细越好，而是先确保“会话、编排、求解”三者各有清晰归属。这样后续优化时不会互相牵连。

## 3. 状态机设计

### 3.1 会话状态机

第一版建议把一个 ML 会话收敛成 6 个状态：

| 状态 | 含义 |
|---|---|
| `draft` | 会话刚创建，还没有形成明确任务 |
| `discussing` | 用户与 agent 正在讨论数据、目标、指标和约束 |
| `ready` | 已形成结构化任务草案，等待用户确认执行 |
| `running` | 正在调用 `autogluon-assistant` 执行求解 |
| `optimizing` | 基于已有结果继续优化或继续试验 |
| `completed` | 当前执行流程结束，已有稳定产物和摘要 |

这个状态机的设计原则是“够用而不膨胀”。第一版最怕的不是状态太少，而是状态过多导致每个流程都要写一套特殊规则。实际上，只要能把讨论、确认、执行、继续优化这几个关键阶段收稳，大部分业务体验就已经是完整的。更复杂的状态，例如“审阅中”“审批中”“归档中”，完全可以在企业业务层补，而不必硬塞进第一版的 ML 编排状态机里。

### 3.2 状态切换规则

建议第一版的状态切换遵循下面的主路径：

1. `draft -> discussing`
   - 用户上传数据或给出初始任务描述
2. `discussing -> ready`
   - 已经补齐必要关键信息，并生成结构化任务草案
3. `ready -> running`
   - 用户明确确认执行
4. `running -> optimizing`
   - 已经有可用结果，用户要求继续优化
5. `running -> completed`
   - 达到停止条件，当前求解流程结束
6. `completed -> optimizing`
   - 用户在已有结果上继续追加约束或继续试验

在这套规则里，最重要的不是“状态转移够不够多”，而是“哪些转移必须被禁止”。例如，`draft` 状态下不能直接进 `running`，否则讨论环节就被绕开了；`running` 状态下也不应该把新输入立即当成对当前单轮执行的热修改，而应该先记录为下一轮生效的约束。这样做看起来更保守，但恰恰是贴近当前代码现实的设计。

### 3.3 输入类型怎么识别

建议把用户输入粗分成五类：

| 输入类型 | 典型例子 | 建议处理方式 |
|---|---|---|
| 任务描述 | “帮我做一个客户流失分类模型” | 进入讨论态，补充上下文 |
| 约束补充 | “只能用 CPU，指标看 F1” | 更新任务草案 |
| 执行确认 | “可以开始训练了” | 从 `ready` 进入 `running` |
| 轮间修正 | “不要再尝试多模态” | 写入后续轮次约束 |
| 优化或分叉 | “基于当前结果再试一版” | 进入 `optimizing` 或创建分支 |

第一版不需要把意图识别做成复杂模型系统。更可行的方式，是把这部分优先放在 ACP 轻编排层：先用规则识别作为主路径，再用 LLM 辅助处理边界表达，把输入先分流到讨论、确认、轮间修正或继续优化这些会话动作上。只要系统稳定地把输入落到正确的阶段动作上，业务价值就已经很明显。

### 小结

状态机的目标不是覆盖所有边角情况，而是保证“讨论、执行、优化”三条主线不打结。第一版只要在这个层面稳定，就已经足够。

## 4. 接口草案

### 4.1 设计原则

从整体设计上看，不建议把所有业务能力都直接硬塞进 ACP 方法里。更合理的方式，是让 ACP 继续承担标准会话协议和主动控制语义，而业务系统通过自己的 HTTP API 管理会话元信息、文件上传、执行确认和结果访问。这样协议层和业务层边界会更清楚，也更容易让前端复用 ACP 现有能力。

同时，这里也要把一个常见误区说清楚：当前 ACP 命令并不是一个原生对外 HTTP 服务，因此企业平台如果要走 Web/服务端集成，现实路径通常是“业务 HTTP API + 内部 ACP bridge”这种组合，而不是直接把 ACP 当成公网标准 HTTP 接口。

### 4.2 建议的业务接口

建议业务侧至少补这些接口：

| 接口 | 作用 |
|---|---|
| `POST /ml/session/create` | 创建业务会话并映射 ACP session |
| `POST /ml/session/upload` | 上传数据目录或样本文件 |
| `POST /ml/session/confirm` | 确认当前任务草案并开始执行 |
| `POST /ml/session/interrupt` | 中断当前执行 |
| `POST /ml/session/optimize` | 基于当前结果继续优化 |
| `POST /ml/session/fork` | 从当前结果创建实验分支 |
| `GET /ml/session/result` | 获取结果摘要和产物索引 |

会话创建接口示例：

```json
POST /ml/session/create
{
  "projectId": "proj_123",
  "workspaceId": "ws_001",
  "title": "客户流失预测",
  "initialPrompt": "帮我做一个客户流失分类模型"
}
```

建议返回：

```json
{
  "businessSessionId": "mlsess_001",
  "acpSessionId": "sess_xxx",
  "status": "draft"
}
```

任务确认接口示例：

```json
POST /ml/session/confirm
{
  "businessSessionId": "mlsess_001",
  "taskSpec": {
    "inputDir": "/data/workspaces/u1/mlsess_001/input",
    "targetColumn": "churn",
    "problemType": "binary",
    "metric": "f1",
    "maxIterations": 5,
    "preferredTools": ["autogluon.tabular"],
    "resourcePolicy": {
      "gpuAllowed": false,
      "timeBudgetMinutes": 20
    }
  }
}
```

### 4.3 ACP 侧建议怎么用

第一版不建议发明太多新的私有 ACP 方法，而建议充分利用现有能力，把 ACP 明确用成“轻编排 + 主动控制入口”：

| ACP 能力 | 在 ML 场景中的建议用法 |
|---|---|
| `newSession` | 创建新的 ML 会话 |
| `prompt` | 承载讨论、确认和轮间修正输入 |
| `forkSession` | 基于当前求解结果分叉实验 |
| `resumeSession` | 恢复历史会话 |
| `setSessionMode` | 在讨论、执行、优化等模式之间切换 |
| `setSessionConfigOption` | 切换模型 effort、策略档位或业务定义控制项 |
| `available_commands_update` | 主动公开当前阶段可执行命令 |
| `plan` | 把当前任务计划、下一轮建议和任务拆解回传给客户端 |
| `tool_call` / `tool_call_update` | 承载执行状态、工具运行和结果变化 |
| `requestPermission` | 在关键操作前触发显式确认 |

在这个组合里，`ACP Capability Broker` 是一个很关键的实施点。它的职责不是发明新协议，而是把会话级轻编排能力组织起来，根据当前业务状态决定“ACP 当前该公开什么、当前输入应该被理解成什么”。例如，在 `discussing` 状态下，Broker 可能把一条新输入识别为“约束补充”而不是“执行确认”，同时只公开“补充目标列”“确认评价指标”“确认资源预算”；到了 `ready` 状态，再公开“开始执行”；进入 `completed` 后，再公开“继续优化”“基于当前结果分支”。这会让 ACP 的主动性真正落到业务体验里，而不只是停留在代码能力表上。

### 小结

接口设计最重要的不是把一切都塞进一个协议，而是让 ACP 做它擅长的会话轻编排与主动控制，让 HTTP 业务面做它擅长的元信息、文件和结果管理。

## 5. 事件流与数据结构

### 5.1 建议的数据结构

第一版建议至少补两张业务表：业务会话表和任务执行表。重点不是一开始把字段铺得多全，而是确保“业务会话”和“ACP 会话”能稳定映射，并且每次执行都有独立记录。

业务会话表建议至少包含：

| 字段 | 作用 |
|---|---|
| `business_session_id` | 业务会话号 |
| `acp_session_id` | 对应 ACP 会话号 |
| `project_id` | 项目归属 |
| `workspace_id` | 工作区归属 |
| `status` | 当前状态，如 `discussing`、`running` |
| `current_task_spec` | 当前结构化任务定义 |
| `current_run_id` | 当前执行实例 |
| `best_result_ref` | 当前最佳结果引用 |
| `created_at` / `updated_at` | 生命周期追踪 |

任务执行表建议至少包含：

| 字段 | 作用 |
|---|---|
| `run_id` | 执行实例号 |
| `business_session_id` | 所属业务会话 |
| `phase` | 讨论、执行或优化 |
| `iteration_no` | 当前迭代号 |
| `status` | 执行状态 |
| `score` | 当前分数或摘要分数 |
| `artifact_dir` | 产物目录 |
| `log_ref` | 日志索引位置 |

### 5.2 建议的事件流

第一版不需要把求解器内部每一个细节都结构化成前端事件，但至少应让用户看到一条完整的求解会话流。建议先收敛成下面几类事件：

| 事件类型 | 触发时机 |
|---|---|
| `discussion_update` | 数据理解结果、澄清问题、任务草案生成 |
| `execution_started` | 用户确认后开始正式求解 |
| `iteration_update` | 每轮迭代开始或结束 |
| `tool_update` | 代码执行开始、进行中、结束或失败 |
| `score_update` | 验证分数变化或最佳结果刷新 |
| `result_update` | 当前结果摘要、产物位置、下一步建议 |

这些事件最终都可以由 `Event Translator` 转成 ACP `sessionUpdate`。如果当前会话状态发生变化，还可以同步触发 `plan`、`available_commands_update` 或配置项更新，让客户端不仅知道发生了什么，也知道下一步可以做什么。这一点很重要，因为它决定了 ACP 的主动性是否真正被发挥出来。

### 5.3 轮间修正数据怎么落

对“轮间修改”这个关键能力，第一版建议不要做得太重。比较稳妥的方式，是先由 ACP 轻编排层判断这条输入属于“轮间修正”，再在业务侧维护一份“pending constraints”或“next-iteration overrides”，把用户在 `running` 或 `optimizing` 阶段追加的新要求先存起来。当前轮执行不打断，等下一轮开始前，由 `Task Spec Builder` 把这部分约束合并到新的求解上下文中，再进入下一次 `manager.step()`。

这种做法的优点是简单、真实、容易验证，而且和当前代码实现边界高度一致。它不承诺单轮内部热修改，但已经足够让用户在训练过程中继续掌控求解方向。

### 小结

第一版数据结构和事件流的目标，不是把平台做成实验系统全集，而是先确保会话、执行和优化三条线都能被可靠记录和可靠回传。

## 6. 实施步骤与风险

### 6.1 MVP 建议推进顺序

建议第一版按下面顺序推进：

1. 先建立业务会话与 ACP session 的映射表。
2. 先补 ACP 轻编排能力，再实现 `ML Session Orchestrator` 的基础状态机与上下文存储。
3. 打通“讨论态 -> 任务草案 -> 用户确认 -> 执行态”的最小闭环。
4. 先用 `run_agent()` 接 `autogluon-assistant`，不急着深入改 `NodeManager`。
5. 通过日志、状态和输出目录先做粗粒度事件回传。
6. 在此基础上补“轮间修正”能力，让新增约束在下一轮生效。
7. MVP 稳定后，再考虑补更细粒度的迭代钩子、实验分叉管理和更强执行隔离。

### 6.2 主要风险点

第一版最大的风险不是技术上做不出来，而是容易过度设计。最常见的几个风险是：一开始就想做完整多租户实验平台；一开始就想把所有求解器内部事件都结构化；一开始就想把 `NodeManager` 彻底改造成新的编排框架；一开始就把 ACP 写成原生对外 HTTP 控制面。这些方向都会显著拉长周期，但并不是 MVP 价值成立所必需的条件。

另一个需要提前说明的风险，是执行隔离。`autogluon-assistant` 会生成和执行真实代码，OpenCode 当前也有本地 PTY 与工作目录能力，所以如果企业场景接触敏感数据或不可信输入，后续一定需要把 Runner/容器隔离补上。只是这个问题更适合作为第二阶段的工程重点，而不是阻塞第一版验证。

### 6.3 最终建议

比较稳妥的落地路径是：

1. 把 ACP 当成统一会话、轻编排与主动控制入口，而不是只当消息通道。
2. 增加轻量 Orchestrator，把会话信息沉淀为结构化 ML 任务，并承接持久化执行控制。
3. 保留 `autogluon-assistant` 现有求解内核，不在第一版做深改。
4. 明确把交互能力收敛到“轮与轮之间插入修改”。
5. 先追求最小闭环稳定，再逐步补细粒度事件、隔离和治理。

### 小结

实施设计的关键，不是一次把所有能力铺满，而是先把“会话、任务、执行、反馈”四条链真正接通。只要 ACP 的主动能力被正确承接，`autogluon-assistant` 的求解能力被稳定利用，并且轮间修正这件事跑顺，第一版就已经具备很强的产品成立性。
