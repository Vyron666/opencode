# 企业级 OpenCode ACP 执行内核部署方案

## 1. 方案结论

如果从“`opencode` 能不能直接作为企业里的统一 Agent 平台对外提供服务”这个问题出发，最重要的不是先看它能不能启动一个 `ACP` 会话，而是先看它当前代码里真正稳定的边界在哪里。结合现有实现，更准确的判断是：`opencode` 很适合被部署成企业 Agent 体系里的 `ACP agent` 执行内核，也适合作为有状态 Worker 承接真实会话与工具执行，但它并不适合在第一层就被定义成企业最外侧的公共无状态 API 平台。`ACP` 当前已经具备会话生命周期、主动事件回传、模式切换、命令公开、计划更新和会话分叉等能力；OpenCode 本体也已经具备工作区路由、PTY 执行、worktree 管理、会话落库和实例级状态缓存这些很强的执行侧能力。但这些能力组合起来，更像一个“强执行、强会话、强上下文绑定”的执行内核，而不是一个天然可被公网直接横向打平的标准企业接入层。

这一定义很关键，因为企业生产部署真正关心的，从来不只是“能不能跑起来”，而是“会话落到哪台机器、执行过程是否可恢复、任务中断后怎么续跑、不同用户会不会串状态、某个 Worker 挂了以后怎么接手、日志和产物怎么归档、审计链路怎么补齐、后续怎么做多实例扩缩容”。在这些问题上，`opencode` 当前提供的是非常有价值的执行基础设施，但它把很多关键状态留在了实例内、目录内和本地资源里。也正因为如此，更合理的企业落地方式不是把它直接当成最外层平台，而是把它放到“控制面 + 桥接层 + 执行层”结构里的执行内核位置，让外层系统承担身份、会话归属、路由治理、审计、存储和多实例调度。

从代码证据看，这个判断是有明确依据的：

| 能力 | 代码位置 | 当前结论 |
|---|---|---|
| ACP 入口 | `packages/opencode/src/cli/cmd/acp.ts` | `opencode acp` 当前通过 `stdio` 的 NDJSON/JSON-RPC 对外提供 ACP，不是原生 HTTP ACP 服务 |
| ACP 会话状态 | `packages/opencode/src/acp/session.ts` | ACP 会话状态保存在进程内 `Map`，天然依赖实例本地内存 |
| 本地会话与命令执行 | `packages/opencode/src/pty/index.ts` | PTY 直接绑定宿主机本地进程与 WebSocket 订阅，不是无状态执行面 |
| 工作目录隔离 | `packages/opencode/src/worktree/index.ts` | worktree 提供目录级隔离与派生工作副本，但不是企业级强沙箱 |
| 实例级缓存 | `packages/opencode/src/effect/instance-state.ts` | 多类运行态缓存以实例上下文和目录为作用域，明显依赖单实例状态 |
| 工作区路由 | `packages/opencode/src/server/routes/instance/httpapi/middleware/workspace-routing.ts` | 已支持按 workspace/session 做本地与远端路由，适合被上层控制面利用 |
| 工作区目标模型 | `packages/opencode/src/control-plane/types.ts` | 已存在 `local`/`remote` target 抽象，但不是完整企业调度中心 |
| 数据库存储 | `packages/opencode/src/storage/db.ts` | 默认 SQLite + WAL，更适合单机或有限共享场景，不适合直接做高并发多实例中心库 |
| 全局事件总线 | `packages/opencode/src/bus/global.ts` | 当前更偏实例内事件广播，不是天然跨实例事件总线 |

### 小结

`opencode` 最适合被定义成企业 Agent 体系里的执行内核，而不是企业最外侧平台本身。它强在真实会话、真实上下文和真实执行，弱在天然无状态化与中心化治理。部署设计应该顺着这个事实来，而不是反着改写。

## 2. 现有能力与部署边界

### 2.1 为什么说它适合做执行内核

从执行视角看，`opencode` 的优势并不零散，反而相当完整。它已经把会话、工具调用、终端执行、项目目录、工作区路由、事件流和本地持久化放到了同一套运行模型里。对于企业来说，这意味着它不是一个只会吐文本的对话壳，而是一个能够真正承接“有上下文、有目录、有命令、有产物”的 Agent 执行进程。`ACP` 让外层系统可以用统一协议接住会话与主动回传，OpenCode server 让内部执行能力可以被稳定调用，`pty` 和 `worktree` 让实际的开发式、自动化式任务有了落地载体，SQLite 会话存储又让基本的恢复和查询有了抓手。

这类能力组合，在企业生产环境里其实很难得。很多系统擅长接请求，但不擅长维持长会话；有些系统擅长调模型，但不擅长承接真实命令执行；还有些系统会做编排，但缺乏真正细粒度的工作区和执行状态。`opencode` 恰好不是这样。它天生更像一个“带状态的 Agent 执行器”。这也是为什么更合理的部署思路，不是把它削成一层过薄的无状态 API，而是承认它的状态性、利用它的状态性，再通过企业自己的控制面把这种状态管起来。

### 2.2 为什么说它不适合直接做最外层公共平台

问题不在于它能力不够，而在于它当前的状态组织方式决定了它不适合被简单当作“来一台就加一台”的公共入口。最典型的例子就是 `packages/opencode/src/acp/session.ts` 里的 ACP session manager，它把会话状态保存在进程内 `Map`；同样，`packages/opencode/src/pty/index.ts` 里的 PTY 会话直接绑定本地进程、缓冲区和 WebSocket 订阅；`packages/opencode/src/effect/instance-state.ts` 里又大量使用了按实例目录作用域的缓存。换句话说，很多重要状态并没有天然抽离成跨实例共享资源，而是明确附着在当前实例、当前目录和当前宿主机执行环境上。

数据库也体现了类似边界。`packages/opencode/src/storage/db.ts` 默认打开的是本地 SQLite 数据库，并启用 WAL、busy timeout 和本地缓存优化。这说明它非常适合单机或少量受控实例场景下的高效落地，但并不意味着它已经天然具备多实例共享中心数据库那套治理假设。只要架构上误把它当成无状态控制面，很快就会遇到“请求打到了错误实例”“会话恢复不到原状态”“一个实例能看到另一个实例的数据库却接不上它的本地进程”这种典型错位。

### 2.3 ACP 的主动性在部署里应该怎么理解

这里尤其要避免另一个常见误解：既不能把 ACP 写成“只是一个消息协议层”，也不能把它夸大成“当前已经是标准企业 HTTP 控制平面”。更准确的描述是，ACP 已经具备很强的主动会话控制语义，但它当前的暴露方式仍然是 `stdio` 协议服务。也就是说，主动性是真的，原生 HTTP 服务化不是。`packages/opencode/src/cli/cmd/acp.ts` 的实现非常清楚地说明了这一点：ACP 命令会先拉起一个 OpenCode HTTP server，再通过 SDK 调用内部服务，对外本身还是 `stdin/stdout` 的 NDJSON/JSON-RPC 会话。

这反而给企业部署一个很明确的答案：不要试图跳过桥接层，应该主动引入 `ACP Bridge`。这层 Bridge 的职责不是削弱 ACP，而是把 ACP 的主动能力网络化、会话化和平台化，让企业前端、IDE、网关和控制面都能稳定接入。换句话说，部署时应该提升 ACP 的地位，把它定义成“主动会话控制协议面”，再用 Bridge 去承担 HTTP/WebSocket 接入、会话绑定、流式转发和事件封装。

### 小结

`opencode` 的强项是有状态执行和主动会话协作，边界是状态天然绑定实例、本地资源和目录。企业部署不该压平这件事，而应该围绕它设计。

## 3. 推荐的企业部署架构

### 3.1 总体结构

比较稳妥的企业级部署方式，建议拆成五层，而不是把所有能力塞进同一个服务进程里：

| 层级 | 作用 | 关键组件 |
|---|---|---|
| 接入层 | 承接 Web、IDE、门户、SSO、审计入口 | API Gateway、SSO、Auth、Rate Limit |
| 会话控制层 | 维护业务会话、路由策略、权限上下文与生命周期 | Session Control Plane |
| 协议桥接层 | 把 HTTP/WebSocket 请求桥接到 ACP，会话流和事件流双向转换 | ACP Bridge |
| 执行层 | 真正运行 ACP agent 与 OpenCode 实例，承接会话、PTY、worktree 与工具调用 | OpenCode Worker |
| 存储治理层 | 保存业务会话、路由映射、产物索引、审计日志与集中指标 | Metadata DB、Artifact Store、Log/Metric Stack |

这五层里，真正运行 `opencode` 的位置应该是执行层。也就是说，企业不要把 OpenCode 当成“最外层平台”，而要把它定义成“Worker 内核”。最外层的 Session Control Plane 负责知道用户是谁、当前会话该去哪里、会话是否已经绑定某个 Worker、某个 Worker 是否还健康、是否需要重建或迁移。ACP Bridge 负责把外部世界和 ACP 协议接起来，并把 ACP 的主动计划、命令、权限请求和事件流按企业能消费的方式暴露出去。OpenCode Worker 则专心承担它最擅长的部分：真实上下文、真实执行和真实状态。

### 3.2 为什么必须保留 Session Control Plane

很多团队在做这类部署设计时，第一反应是想直接让前端去连某个 ACP 实例，或者让网关直接随机打到某个 Worker。这种设计最大的问题，不在于第一天跑不起来，而在于一旦进入真实企业场景，会话就会立刻变成一等公民，而不是普通请求。只要一个会话里已经挂了 PTY、目录、worktree、权限状态和局部缓存，它就天然不能再被当成任意一台机器都能瞬时接手的普通 HTTP 请求。

也正因此，`Session Control Plane` 在这里并不是可选优化，而是整体方案真正成立的前提。它至少要负责三件事。第一，业务 session 和执行 session 的映射，例如 `business_session_id -> acp_session_id -> worker_id -> workspace_id`。第二，会话粘性路由，即同一个会话在活跃期内应持续落到同一个 Worker，除非发生显式迁移或重建。第三，会话元数据治理，包括状态、租户、发起人、超时策略、产物根目录和审计关联。只有这样，OpenCode Worker 才能继续发挥“有状态执行”的优势，而不会被最外层流量随机分发机制破坏。

### 3.3 为什么必须有 ACP Bridge

虽然 ACP 本身已经具备主动计划、命令更新、权限请求和事件流能力，但企业系统通常不会直接把 `stdin/stdout` 的协议进程暴露给 Web、IDE 或门户。Bridge 的意义就在于，它把“ACP 是强协议面”这件事，翻译成“企业系统可集成的网络入口”。它可以对外提供 HTTP 或 WebSocket 接口，对内则维护与目标 Worker 上 ACP 进程的长连接或会话通道。

更重要的是，Bridge 还承担协议语义转换。比如用户发起一条“继续当前会话”的请求时，Bridge 需要先从控制面拿到目标 Worker 和 ACP session，再把外部输入映射成 ACP prompt 或 session 操作；当 Worker 回传 `plan`、`available_commands_update`、`requestPermission` 或 `tool_call_update` 时，Bridge 又需要把这些事件转成前端可理解、业务侧可审计的事件流。也就是说，Bridge 不是一个纯转发层，而是企业部署里让 ACP 主动性真正可落地的“协议适配面”。

### 小结

推荐结构不是“网关直连 OpenCode”，而是“Session Control Plane + ACP Bridge + OpenCode Worker”。这样既不浪费 OpenCode 的状态执行能力，也不把企业治理职责压错位置。

## 4. 会话路由、隔离与扩缩容

### 4.1 会话为什么必须做粘性路由

这套部署里最重要的一个原则，就是会话必须按粘性路由处理。原因并不抽象，完全来自当前代码现实。ACP 会话状态在进程内 `Map`，PTY 会话绑定本地子进程和本地缓冲区，worktree 绑定本地目录和本地 git 副本，`InstanceState` 又会基于当前目录维持 scoped cache。只要这些状态还存在于某个 Worker 上，这个会话就不应该被随机切换到另一台实例上继续执行。

因此，生产部署里建议至少按以下优先级做会话定位：

| 路由键 | 作用 |
|---|---|
| `business_session_id` | 业务侧统一主键，用于查找完整会话归属 |
| `acp_session_id` | 对应 ACP 会话标识，用于桥接层与 Worker 协作 |
| `workspace_id` | 用于绑定具体工作区和远端/本地目标 |
| `worker_id` | 表示当前粘附的执行实例 |
| `project_id` | 辅助产物归档、目录治理与配额控制 |

只要会话还处于活跃执行期，就应该优先按 `worker_id` 命中原实例；只有实例失活、会话显式结束或人工触发恢复时，控制面才应该考虑重建路径，而不是让网关自动重试到另一台 Worker。

### 4.2 多实例扩容应该怎么理解

从部署策略上说，`opencode` 并不是不能多实例部署，而是不能把“多实例”理解成“前面随便挂个负载均衡、后面随便扩几个副本”。更准确的说法是：它适合做“多 Worker 扩容”，不适合做“无状态副本池扩容”。前者承认每个 Worker 都是有状态执行单元，扩容的核心是新增可分配的执行槽位；后者则假设任何请求都能随意漂移，这和当前实现是冲突的。

因此，企业如果要上服务器部署，通常应该做好多实例 Worker 规划。原因不是单实例绝对扛不住，而是企业真实场景里会同时遇到三类压力：第一类是长会话并发，多个用户会同时维持活跃 session；第二类是资源竞争，PTY、文件系统、模型调用和工具执行都会占资源；第三类是故障域隔离，一台 Worker 出现阻塞或异常时，不应拖垮所有会话。把 OpenCode Worker 做成可注册、可摘除、可观测的多实例执行池，会比试图把它包装成单个“大而全”的服务稳妥得多。

### 4.3 隔离边界应该怎么定义

`worktree` 能提供目录级隔离，`workspace-routing` 能提供工作区路由，PTY 能提供执行通道，但这三者都不等于企业级强隔离。尤其在涉及不可信输入、外部仓库、执行脚本和敏感资料时，部署设计里必须把 OpenCode Worker 看成“需要被容器或 Runner 包裹的执行内核”。比较稳妥的边界通常包括：一会话一工作目录、按租户或项目分配产物前缀、Worker 进程级资源限制、必要时一任务一容器或一租户一隔离池、网络出口白名单以及审计日志留存。

这也是为什么文档里不应该把 `worktree` 直接写成“安全沙箱”。它很有价值，但它解决的是项目副本和目录派生问题，不是企业安全边界问题。部署上应该承认这一点，再由外层 Runner、容器编排或宿主机策略补上真正的执行隔离。

### 小结

多实例部署是推荐项，但前提是按“有状态 Worker 池”来设计，而不是按“无状态 API 副本”来设计。会话粘性路由是这个前提里最不能放松的一条。

## 5. 生产落地建议

### 5.1 第一阶段先做到什么程度

第一阶段不建议一上来就追求完整企业控制平面。更务实的目标，是先把“控制面知道会话归属、Bridge 能稳定桥接、Worker 能稳定承接执行”这三件事跑通。只要企业能够创建业务 session、把它映射到某个 OpenCode Worker、在整个会话活跃期内持续路由到同一个 Worker，并把关键事件、日志和产物稳定归档，这套部署模型就已经成立。

比较适合的第一阶段范围通常是：

- 有限数量的 OpenCode Worker
- 单区域部署
- 明确的会话粘性路由策略
- 独立的业务元数据存储
- 对象存储或共享文件存储保存产物
- 日志、指标和审计链路先打通

### 5.2 第二阶段再补什么

| 能力 | 为什么适合后置 |
|---|---|
| Worker 自动摘除与重建 | 依赖控制面、健康检查和恢复策略成熟 |
| 容器化强隔离执行 | 依赖基础设施、镜像治理和资源编排 |
| 多租户资源配额 | 需要租户模型、计量口径和隔离池策略 |
| 跨机恢复与回放 | 需要更细的会话快照与执行恢复语义 |
| 完整审计与成本核算 | 需要事件、日志、产物与身份映射全部打通 |

### 5.3 最终建议

比较合理的最终形态，不是让 OpenCode 自己演化成最外层平台，而是让它稳定地待在最擅长的位置上。企业网关负责身份与接入，Session Control Plane 负责会话归属与粘性路由，ACP Bridge 负责协议网络化与主动事件暴露，OpenCode Worker 负责真实执行与上下文承载，外层存储与治理体系负责审计、产物、监控和隔离。只要这几个角色边界不混，OpenCode 反而能够在企业里发挥出比“直接暴露成一个 API 服务”更大的价值，因为它不会被迫削弱自己最有用的那部分能力。

### 小结

这份部署方案的核心不是“怎么把 OpenCode 包装得像无状态平台”，而是“怎么承认它是有状态执行内核，并把这种状态性放进企业治理框架里”。只要这个前提立住，多实例部署、会话控制和生产治理都会顺很多。
