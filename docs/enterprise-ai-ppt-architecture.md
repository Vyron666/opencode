# 企业内部 AI PPT 方案设计

## 1. 方案结论

如果从“企业内部要不要把这套东西拿来做 AI PPT”这个问题出发，最重要的不是先看它能不能生成一份 `pptx`，而是先看它在整条链路里应该扮演什么角色。结合当前代码，更准确的判断是：这套项目可以作为企业内部 AI PPT 平台的核心底座，但它本身还不是一个现成的企业级平台。`ppt-master` 已经把“资料转 Markdown、项目初始化、策略锁定、逐页 SVG 生成、质量检查、后处理、导出 PPTX”这条生产链做得相当明确；`ACP` 则不是简单的消息接口，而是已经具备了统一会话承载、模式切换、配置切换、命令公开、计划回传、权限请求回传、工具状态回传和会话分叉等能力。两者放在一起看，更合理的组合不是“一个会话协议层外加一个 PPT skill”，而是“一个轻编排与主动会话控制入口外加一条明确的内容生产流水线”。

这一定义很关键，因为企业在接入 AI PPT 时真正关心的，往往不是“模型能不能画一页图”，而是“这次请求是谁发起的、看过哪些资料、哪些页面需要确认、哪些步骤能自动推进、哪些产物需要审阅、最终文件怎么归档、出错时怎么回放、多人情况下怎么避免串会话”。在这些问题上，`ppt-master` 和 `ACP` 分别已经覆盖了生产和控制的两个重要侧面，但都没有直接变成企业治理体系本身。企业真正需要补的是外层身份、权限、审批、存储、审计和执行隔离，而不是重新从零发明一套 PPT 生产内核。

从代码证据看，这个判断是有落点的：

| 能力 | 代码位置 | 当前结论 |
|---|---|---|
| ACP 入口 | `packages/opencode/src/cli/cmd/acp.ts` | `opencode acp` 通过 `stdio` 的 NDJSON/JSON-RPC 对外提供 ACP，会话背后再调用 OpenCode HTTP server |
| ACP 会话与事件 | `packages/opencode/src/acp/agent.ts` | 已支持新建/加载/列举/恢复/关闭会话，声明了 fork 能力，且代码中提供 `unstable_forkSession`、模式切换、配置切换、模型切换、命令更新、计划回传、权限请求、工具状态回传 |
| Session 数据模型 | `packages/opencode/src/session/session.sql.ts` | 已有项目、工作区、父会话、消息、todo、权限等结构，但没有企业租户/用户隔离字段 |
| OpenCode HTTP 会话面 | `packages/opencode/src/server/routes/instance/httpapi/groups/session.ts` | 已有实验性的 session HttpApi 路由，可作为企业编排层的内部候选能力面，但稳定性与治理仍需外层补齐 |
| 工作区路由 | `packages/opencode/src/server/routes/instance/httpapi/middleware/workspace-routing.ts` | 已支持按 workspace/session 做本地或远端路由 |
| 本地命令执行 | `packages/opencode/src/pty/index.ts` | 通过 PTY 启动本地 shell/进程，不是安全沙箱 |
| 项目隔离 | `packages/opencode/src/worktree/index.ts` | 通过 git worktree 做目录级隔离，但不是企业级执行隔离 |
| PPT 生产流水线 | `.opencode/skills/ppt-master/SKILL.md` | 明确要求串行分阶段执行，包含策略确认、逐页 SVG、质量检查、导出等环节 |

### 小结

这套项目适合被定义为企业 AI PPT 平台的“底座”，但不适合直接被定义成“平台本身”。`ACP` 更适合承担统一会话、轻编排与主动控制入口，`ppt-master` 更适合承担可追踪的内容生产链，外层平台负责治理和集成。

## 2. 现有能力与边界

### 2.1 ACP 已经具备的，不只是“聊天接口”

如果只把 ACP 理解成“客户端把 prompt 发给 agent，agent 再吐回文本”，会明显低估它在这个项目里的作用。结合 `packages/opencode/src/acp/agent.ts`，ACP 当前已经覆盖了几类很关键的能力：第一类是会话生命周期能力，包括 `newSession`、`loadSession`、`listSessions`、`resumeSession`、`closeSession`，并声明了 fork 能力，代码里对应实现是 `unstable_forkSession`；第二类是会话控制能力，包括 `setSessionMode`、`setSessionConfigOption`、`unstable_setSessionModel`；第三类是主动回传能力，包括 `requestPermission`、`tool_call`、`tool_call_update`、`agent_message_chunk`、`agent_thought_chunk`、`plan`、`available_commands_update`、`usage_update` 等事件流。

这意味着，ACP 在企业 PPT 场景里不应该只被放在“消息通道”这个位置上。更合适的理解是，它已经是一个“协议化的轻编排与主动会话控制入口”。外部前端、IDE 或企业门户可以不直接理解 OpenCode 内部的 session、todo、permission、tool part 和 message part，只需要理解 ACP 暴露出来的会话和事件流，就能接住会话、命令、计划、权限请求和执行状态。更进一步说，像“当前输入是在补资料、确认模板方向，还是要求进入生成阶段”这类会话级判断，也可以先由 ACP 层承担。对于企业集成来说，这种能力的价值不在于多了一个协议名词，而在于它把“怎么和 agent 协作”这件事做成了比较稳定的控制面。

不过这里也必须把边界说清楚。当前 `packages/opencode/src/cli/cmd/acp.ts` 的实现说明，ACP 命令对外仍然是 `stdin/stdout` 流式通信，而不是“天然就是一个对外可调用的 HTTP ACP 服务”。它内部确实会先起一个 OpenCode HTTP server，再用 SDK 去调，但那是 OpenCode 内部实现细节，不等于企业可以直接把 ACP 当成标准 HTTP 对外暴露。因此更准确的说法应该是：ACP 已经具备较强的主动会话控制能力，但它的网络化暴露方式仍然需要外层 bridge 或宿主集成来补。

### 2.2 `ppt-master` 已经具备的，是一条严格生产链

`.opencode/skills/ppt-master/SKILL.md` 体现出的重点，不是“会生成 PPT”，而是它把生成过程工程化了。它明确要求流程串行推进，要求在策略阶段完成关键确认，要求逐页生成 SVG，要求每页都受 `spec_lock.md` 约束，要求先过质量检查再导出，要求不允许跨阶段预写内容，也不允许在执行页生成时走批量脚本路径。这套约束看起来很重，但它恰恰符合企业 PPT 的真实诉求，因为企业内部演示文稿往往不怕“步骤多”，怕的是“不可控、不可追踪、不可复现”。

从集成视角看，`ppt-master` 最值得保留的价值有三点。第一，它把内容生产拆成了企业更容易治理的阶段，例如资料输入、策略锁定、页面生成、质量检查和导出；第二，它天然支持“先确认再执行”的工作方式，而不是一上来就直接生成终稿；第三，它已经形成了围绕 `design_spec.md` 和 `spec_lock.md` 的执行契约，这对于企业侧做审阅、复盘和再次加工都很有帮助。换句话说，`ppt-master` 更像一条“受控内容生产流水线”，而不是一个黑盒生成器。

### 2.3 现有能力还缺什么

虽然 `ACP` 和 `ppt-master` 分别在控制和生产两个方向上都已经不弱，但把它们直接拼起来，还不能自动等于“企业 AI PPT 平台”。主要差距有三类。第一类是身份与权限差距。当前 session 数据模型没有天然的 `tenant_id`、`user_id`、`department_id` 这些企业隔离字段，而且 `authenticate()` 当前直接抛出 `Authentication not implemented`，还没有落地成真正的企业身份机制。第二类是业务流程差距。`ppt-master` 自己知道什么时候应该进入策略阶段、执行阶段和导出阶段，但它并不知道企业里的“谁有权确认模板”“哪些 deck 需要审批”“哪个结果应该发回门户还是 IM”。第三类是执行安全差距。OpenCode 当前有 PTY 和 worktree，但这更多是本地执行与目录级隔离，不等于企业所需的容器、沙箱、网络白名单和资源治理。

也正因为如此，文档里对 ACP 的定位需要积极一些，但不能夸大。它已经很适合承担轻编排与主动会话控制入口，但还不是现成企业控制平面；`ppt-master` 已经很适合承担受控生成链，但还不是企业审批系统的一部分。真正要落地时，企业平台需要在它们外层再放一层编排与治理。

### 小结

在当前代码边界内，`ACP` 解决的是“怎么把 agent 的会话和控制能力稳定暴露出来”，`ppt-master` 解决的是“怎么把 PPT 生产过程做成受控流水线”。企业要补的是治理层，而不是重做这两层。

## 3. `ACP + ppt-master` 应该怎么组合

### 3.1 先说推荐结论

最稳妥的接法，不是让 ACP 直接取代 `ppt-master` 去“生成 PPT”，也不是让 `ppt-master` 自己同时承担前端交互、会话状态和企业审批。更合适的组合方式是：用 ACP 统一承载会话、轻量意图识别、命令、计划、权限和状态广播，用 `ppt-master` 执行实际的 PPT 生产流水线，再在中间加入一层企业自己的 Orchestrator 负责把更重的业务意图翻译成阶段动作和持久化状态。这一层不需要重新发明 PPT 生成逻辑，它的核心职责是衔接会话语义与生产语义。

这层 Orchestrator 的存在，是为了把“用户想做一个汇报材料”变成几类更明确的动作，但不是要把所有判断都吞进去。例如，用户刚上传资料时，系统应该先进入讨论和需求收敛，而不是马上生成；这类会话级阶段判断完全可以先由 ACP 层承担。等到用户确认结构和视觉方向后，系统再进入 `ppt-master` 的策略锁定与执行阶段；如果生成过程中需要补资料、改模板或调整页数，ACP 可以先识别这是哪类会话动作，并通过命令更新和计划回传，把当前能做什么清晰公开给前端，而 Orchestrator 再承接更重的阶段推进、持久化和结果管理。这样，PPT 生成就不再是一条黑盒任务，而是一条可以被会话层主动控制和企业业务层理解的生产流。

### 3.2 ACP 在这条链路里具体做什么

ACP 在企业 AI PPT 场景里，应该承担四类能力。第一类是统一会话承载，让来自 Web、IDE、企业门户或 IM 的多轮交互进入同一个 session，并保持可恢复、可追踪。第二类是主动控制公开，通过 `available_commands_update`、`plan`、`setSessionMode`、`setSessionConfigOption` 把当前阶段允许执行的动作明确暴露出去，例如“生成大纲”“确认策略”“开始逐页生成”“重新导出”“从当前结果分支”。第三类是执行流广播，把 `tool_call`、`tool_call_update`、消息分片、思考分片、权限请求等事件变成前端可见的进度和动作流。第四类是会话分叉，让已有 deck 可以不必整单重来，而是在当前上下文基础上继续修订、分支试验或做不同版本输出。

这里尤其值得强调的是“主动性”。很多系统虽然也有对话接口，但实际上一旦进入执行阶段，就只剩下日志刷屏。ACP 已有的结构恰好允许企业把执行过程组织成更可理解的会话流。例如，在策略锁定完成时回传一份 plan；在进入逐页 SVG 阶段时公开“允许查看预览”“允许暂停后续导出”“允许切到审阅模式”；在某一步需要额外权限或外部资源时触发 `requestPermission`；在导出完成后直接更新命令列表为“下载产物”“继续修指定页面”“创建新分支”。这种“告诉客户端发生了什么，也告诉客户端下一步能做什么”的能力，比单纯的日志输出更适合企业集成。

### 3.3 `ppt-master` 在这条链路里具体做什么

如果说 ACP 解决的是“如何稳定协作”，那 `ppt-master` 解决的就是“如何稳定生产”。它最适合继续保留的职责，是把源材料经过一条严格的串行流水线转成可导出的演示文稿。具体来说，它负责资料预处理、项目初始化、设计策略阶段、必要的图片获取、逐页 SVG 生成、SVG 质量检查、备注生成、后处理和导出。这些职责不适合被拆散到会话层里，因为它们之间本来就存在明确的上下游依赖和执行纪律。

因此，企业平台不应该把 `ppt-master` 改造成“一个随时接受任何自然语言命令的自由 agent”，而应该把它看成“一个可被会话层调度的生产引擎”。也就是说，企业层可以通过 ACP 组织讨论、确认和状态流，但一旦进入某个明确的生产阶段，真正的内容生成顺序仍然要尊重 `ppt-master` 的工作流约束。这样做的好处是，不会因为引入了更强的交互而把原本严谨的生产链冲散。

### 小结

`ACP + ppt-master` 的最优组合不是谁替代谁，而是 ACP 负责把协作变成可控制的会话流，`ppt-master` 负责把内容变成可复现的生产流，企业编排层负责把两者接起来。

## 4. 企业 AI PPT 的总体架构

### 4.1 分层设计

建议把系统拆成五层，这样每一层的边界会比较清楚：

| 层级 | 作用 | 关键组件 |
|---|---|---|
| 接入层 | 接企业门户、Web、IDE、IM、审批入口 | API Gateway、SSO、上传入口、消息入口 |
| 会话控制层 | 承载会话、轻量意图识别、命令、计划、权限请求和状态广播 | ACP、业务会话映射表 |
| 编排层 | 负责重编排、阶段持久化与 PPT 生产推进 | PPT Orchestrator、Template Policy、Review Policy |
| 生产层 | 执行受控的 PPT 生产流水线 | `ppt-master`、SVG 生成、质量检查、PPTX 导出 |
| 治理层 | 负责身份、审批、审计、存储和执行隔离 | IAM、Artifact Store、Audit Log、Runner/Container |

### 4.2 各层边界怎么理解

这里最容易混淆的是会话控制层、编排层和生产层。会话控制层不负责具体 PPT 产出，但也不应该只是被动转发层，它解决的是“谁在当前会话里、当前会话能做什么、当前输入更像补资料、确认方向还是要求进入下一阶段、外部客户端应该看到什么、什么时候触发权限请求、什么时候允许分叉”。生产层不负责企业用户关系和审批逻辑，它解决的是“怎么把已经确认的输入按严格流程生产成高质量 deck”。而编排层才是两者之间真正的桥，它继续承担更重的企业业务语义，例如什么时候应该先走大纲确认、什么时候允许进入执行、什么情况下导出结果要先进入审阅态，而不是立刻对用户可下载。

也就是说，ACP 的主动性不只体现在“把控制能力公开出来”，还体现在“先承担会话级轻编排判断”；而企业编排层的职责则是“承接更重的阶段推进与持久化控制”。例如，在资料刚上传时，ACP 可以先把输入识别为“补资料”或“明确受众”，并只开放“补资料”“确认受众”“选择模板路径”这些动作；在策略锁定后，再开放“开始生成”；在生成完成后，再开放“修订指定页面”“重新导出”“创建分支版本”。这种设计既能充分利用 ACP 的现有能力，也不会让控制权失控。

### 4.3 端到端流程

一次完整的企业 AI PPT 请求，建议这样流转：

1. 用户在企业前端、Web 或 IDE 中发起 PPT 任务并上传资料。
2. 企业网关完成身份校验，得到业务身份与权限范围。
3. 系统创建业务会话，并映射到 ACP session。
4. ACP 先做会话级判断并组织讨论入口，编排层再补齐主题、受众、页数范围、模板要求、品牌约束等关键信息。
5. ACP 通过计划回传和命令更新，把当前阶段可执行动作公开给前端。
6. 用户确认后，编排层驱动 `ppt-master` 进入策略锁定和后续生产阶段。
7. 生产过程中，关键事件通过 ACP 持续回传，包括阶段切换、权限请求、工具执行状态、导出完成和结果可用状态。
8. 产物进入对象存储或业务文件系统，必要时进入审批与审阅流程。
9. 用户可以在当前会话内继续修订，也可以从当前结果分叉出新版本。

### 小结

企业架构的组织方式不应该围绕“模型调用”来设计，而应该围绕“会话、控制、生产、治理、产物”来设计。ACP 和 `ppt-master` 在这个结构里各司其职。

## 5. 多用户隔离与执行安全怎么保证

### 5.1 先说边界

如果只是把 OpenCode 和 ACP 部署到一台服务器上，然后直接让多个企业用户连进来，这并不能自动保证多用户隔离。原因并不复杂：当前 session 结构里没有天然的企业身份字段，ACP 自己也没有完整的企业鉴权实现，PTY 和 worktree 更偏向本地开发态的隔离能力，而不是面向不可信输入的强安全执行边界。所以，多用户隔离这件事必须由外层平台显式承担。

### 5.2 身份与数据边界

企业网关必须先于 ACP 做身份校验。用户进入系统后，外层平台需要先完成 SSO 或统一身份认证，再把 `tenant_id`、`user_id`、`department_id`、角色权限和数据范围映射到业务会话。当前 `session.sql.ts` 中的 `session`、`message`、`part`、`todo`、`permission` 结构可以承载 OpenCode 自己的会话关系，但不足以直接承担企业多租户隔离。因此，企业侧至少应补一张业务映射表，把业务 session 和 ACP session 显式关联起来，并带上租户和用户维度。

建议业务映射至少包含这些字段：

| 字段 | 作用 |
|---|---|
| `business_session_id` | 企业侧会话号 |
| `acp_session_id` | 对应 ACP 会话号 |
| `tenant_id` | 租户归属 |
| `user_id` | 发起人与默认可见范围 |
| `project_id` | 业务项目归属 |
| `workspace_id` | OpenCode 工作区归属 |
| `status` | 当前业务状态 |
| `artifact_root` | 产物目录或对象存储前缀 |

### 5.3 文件与执行边界

PPT 生产流程会产生大量中间文件，例如 Markdown、设计规约、SVG 页面、预览图、备注和导出文件。因此，工作目录绝不能在多用户之间随意共享。比较现实的做法，是按租户、用户、业务会话做目录隔离，并把中间产物和最终产物都放在独立前缀下。`worktree` 可以提供一定的项目级目录隔离，但它并不是安全沙箱；`pty` 可以让命令执行更顺手，但它并不阻止不同任务共享宿主机环境。

如果企业需要接触敏感资料或不可信输入，更稳妥的方式应该是：

- 一任务一 Runner 或容器
- 只挂载当前会话目录
- 网络访问白名单
- CPU/内存/时长限制
- 审计日志留存
- 命令与文件访问边界可追踪

### 5.4 事件与广播边界

ACP 的事件流虽然很适合做前端状态广播，但不能直接把内部事件原样广播给所有用户。比较合理的做法，是把 `requestPermission`、`plan`、`available_commands_update`、`tool_call_update`、消息分片等事件都先附着业务会话上下文，再由企业消息层路由到对应用户或审批链。这样既能保留 ACP 的主动能力，也不会让内部 session 更新越过企业边界直接外溢。

### 小结

多用户隔离不是 ACP 自己打开一个开关就能解决的事情。ACP 能贡献的是会话和控制能力，真正的隔离必须由企业平台在身份、数据、文件、执行和事件几个边界上共同实现。

## 6. 落地建议

### 6.1 第一阶段先做什么

第一版不建议上来就做完整企业平台。更现实的目标，是先把最小闭环跑顺：用户能发起一个企业 PPT 请求，系统能通过 ACP 承载讨论、轻编排和确认，`ppt-master` 能完成受控生成，结果能被稳定回传并归档。只要这一条链路打通，后面的审批、多模板、多租户、复杂权限和大规模调度都还有空间慢慢加。

建议 MVP 的范围控制在：

- 单租户或受控试点租户
- 单条 Runner 或有限容器执行
- 明确的模板或自由设计二选一
- 支持资料上传、策略确认、生成、导出和继续修订
- 支持会话归档与结果回放

### 6.2 第二阶段再补什么

| 能力 | 为什么适合后置 |
|---|---|
| 完整审批链 | 依赖组织结构、角色模型和消息系统打通 |
| 多模板治理 | 需要模板资产管理和品牌策略机制 |
| 多租户隔离 | 需要业务映射、对象存储、执行层一起升级 |
| 强沙箱执行 | 依赖基础设施和安全治理改造 |
| 全量审计与计费 | 需要事件、日志和产物元数据体系成熟 |

### 6.3 最终建议

比较合理的实施方式是：

1. 企业网关先做身份、权限和数据范围校验。
2. ACP 作为统一会话、轻编排与主动控制入口承接前端协作。
3. 企业 Orchestrator 负责把业务流程翻译成策略确认、生成、修订和导出动作，并承接重编排与持久化控制。
4. `ppt-master` 继续承担严格的 PPT 生产流水线。
5. 产物、审批、审计和隔离由企业治理层承接。

### 小结

这不是一个“把模型接上去就能用”的项目，而是一条可以被企业治理的生产链。只要角色边界切得清楚，并且真正把 ACP 的主动控制能力纳入设计，它完全可以演进成企业内部可用的 AI PPT 平台。
