# 企业内部交互式 ML 自动化方案设计

## 1. 方案结论

如果只把这个项目理解成“把一个 AutoML 工具接进聊天窗口”，会低估它真正能提供的价值。结合当前代码，更准确的定位应该是：它可以作为企业内部交互式 ML 自动化平台的核心底座，但它本身不是现成的企业 ML 平台。`autogluon-assistant` 已经把数据理解、工具选择、代码生成、执行评估、验证分数回收和持续试错做成了一条较完整的求解链；`ACP` 则不仅仅是协议入口，而是已经具备会话生命周期管理、模式切换、配置切换、模型切换、计划回传、命令公开、工具状态回传、权限请求回传和会话分叉等能力。把两者放在一起看，更贴切的组合不是“协议接入层 + AutoML 引擎”，而是“轻编排与主动会话控制层 + ML 求解层”。

这个判断背后的关键，不在于系统能不能跑出一轮训练，而在于它能不能把机器学习自动化从“一次性任务投递”升级成“可讨论、可锁定、可执行、可持续优化”的协作过程。真实业务里的 ML 任务，很少在第一句话里就把目标列、指标、资源预算、字段约束、可解释性要求、是否允许 GPU、是否只做表格任务这些信息说完整。只要这些条件没有先对齐，后面即使自动生成了训练代码，结果也经常会偏题。ACP 的价值恰恰在这里体现出来，它让系统不必一开始就直接进训练，而是可以先进入会话、先把任务定义讲清楚，再决定什么时候进入真正的求解阶段。

从代码证据看，当前项目已经具备几块关键基础：

| 能力 | 代码位置 | 当前结论 |
|---|---|---|
| ACP 入口 | `packages/opencode/src/cli/cmd/acp.ts` | 通过 `opencode acp` 启动 ACP，外部通信是 `stdio` NDJSON/JSON-RPC，不是原生 HTTP ACP 服务 |
| ACP 协议与控制 | `packages/opencode/src/acp/agent.ts` | 已支持新建/加载/列举/恢复/关闭会话，声明了 fork 能力，且代码中提供 `unstable_forkSession`、模式切换、配置切换、模型切换、命令更新、计划回传、工具事件回传 |
| ML 主循环 | `autogluon-assistant/src/autogluon/assistant/coding_agent.py` | `run_agent()` 按迭代循环执行 `manager.step()`，不是一次性脚本生成 |
| 搜索式求解核心 | `autogluon-assistant/src/autogluon/assistant/managers/node_manager.py` | `NodeManager` 采用树搜索/MCTS 风格做选择、扩展、模拟和回传 |
| 数据理解 | `autogluon-assistant/src/autogluon/assistant/agents/data_perception_agent.py` | 能从数据目录提取数据画像，形成任务上下文 |
| 工具选择 | `autogluon-assistant/src/autogluon/assistant/agents/tool_selector_agent.py` | 能按任务类型选择更合适的 AutoGluon 工具链 |
| 轮间输入 | `node_manager.py`、WebUI/MCP 相关模块 | 已支持“每轮之间补充输入，下一轮生效”，不支持单轮内部热修改 |
| 当前任务封装 | `autogluon-assistant/src/autogluon/mcp/server/server.py` 等 | 当前以 `start_task`、`check_status`、`cancel_task`、`list_outputs`、`get_progress` 这类任务接口为主，现状更接近任务投递式 MCP，而不是完整交互式会话系统 |

### 小结

这套项目最值得利用的，不是“它能自动写训练代码”，而是“它已经同时具备了轻编排式会话控制能力和自动化求解能力”。企业要做的不是推倒重来，而是把两者正确接起来。

## 2. 现有能力与边界

### 2.1 ACP 已经实现了什么

从 `packages/opencode/src/acp/agent.ts` 来看，ACP 的重点并不在于“它懂不懂机器学习”，而在于“它能不能把 OpenCode 的会话与控制能力标准化暴露给外部客户端”。当前实现里，`newSession`、`loadSession`、`listSessions`、`resumeSession`、`closeSession` 构成了完整的会话生命周期能力，并声明了 fork 能力，代码里对应实现是 `unstable_forkSession`；`setSessionMode`、`setSessionConfigOption`、`unstable_setSessionModel` 提供了显式的会话控制入口；`requestPermission`、`tool_call`、`tool_call_update`、`agent_message_chunk`、`agent_thought_chunk`、`plan`、`available_commands_update`、`usage_update` 则把内部执行过程主动翻译成会话事件流。

也就是说，ACP 现在更像一个“轻编排与主动会话控制层”，而不是一个被动的 prompt 中转接口。对于企业 ML 自动化场景，这一点尤其重要，因为训练请求往往不是一句话就能精确定义的。系统完全可以先通过 ACP 承载讨论，先做会话级意图识别和阶段判断，明确当前输入更像任务描述、约束补充、执行确认还是继续优化，再结合目标列、任务类型、评价指标、资源约束和输出要求把下一步动作组织出来，并通过命令公开和计划回传展示给用户。用户看到的不再只是“给我一句 prompt，我给你一个结果”，而是“当前会话处于什么阶段、已经确认了什么、还能继续做什么”。

不过边界也必须收住。当前 `packages/opencode/src/cli/cmd/acp.ts` 的实现说明，ACP 对外仍然是 `stdin/stdout` 的协议服务，内部再通过 HTTP client 调 OpenCode server。这意味着可以说“ACP 已经适合被 bridge 成企业系统中的主动控制入口”，但不能说“ACP 当前已经原生提供企业可直接调用的 HTTP ACP 服务”。这类区分在架构文档里必须说清楚，否则会把集成成本描述得过轻。

### 2.2 `autogluon-assistant` 已经实现了什么

`autogluon-assistant` 当前最值得保留的，不是某个单点 API，而是它已经形成了一条相对完整的 ML 自动化求解链。`run_agent()` 会加载配置、创建 `NodeManager`、初始化各类 agent，并在迭代循环中不断执行 `manager.step()`；而 `NodeManager` 内部又把每轮求解组织成树搜索式的选择、扩展、模拟和回传过程。这说明它不是“只生成一次脚本”的工具，而是一个会持续试错、会尝试不同路径、会根据验证结果继续优化的求解器。

更重要的是，这套求解器已经带有明显的 ML 领域特征。`DataPerceptionAgent` 会从输入数据目录提取结构化上下文，帮助系统理解当前更像表格、时序还是多模态任务；`ToolSelectorAgent` 会根据任务特征选择更合适的工具链，例如 `autogluon.tabular`、`autogluon.timeseries` 或 `autogluon.multimodal`；`ExecuterAgent` 不只是执行脚本，还会结合 stderr、stdout 和上下文判断当前结果是成功、失败还是值得继续优化。对于企业 ML 自动化平台来说，这些能力比“让通用 coding agent 写一份训练模板”重要得多。

### 2.3 迭代与交互能力到底到哪里

这个问题在设计里必须说准，否则后面会直接影响用户预期。结合 `coding_agent.py` 和 `node_manager.py` 的实现，`autogluon-assistant` 确实具备真实的多轮迭代能力，并且存在“每轮获取用户输入”的钩子。`run_agent()` 外层是一个 `while iteration < max_iterations` 循环，每轮执行一次 `manager.step()`；而 `NodeManager` 在代码生成前会调用 `_get_user_input_for_step()`。第一轮总是使用 `initial_user_input`，后续迭代只有在 `enable_per_iteration_instruction` 打开时才会继续获取新的用户输入；WebUI 和相关后端模块里也已经有 `waiting_for_input` 与 `send_user_input` 这类状态和接口。

因此，比较准确的结论是：`ACP + autogluon-assistant` 完全可以支持“轮与轮之间插入修改”，也就是在上一轮求解完成、下一轮求解开始之前，把新的约束注入当前 session，并在下一轮代码生成与训练执行时生效。但这不等于支持“单轮训练进行到一半时实时热修改内部执行逻辑”。第一版方案里，如果把能力明确收敛到轮间修改，既符合代码现实，也足够有业务价值。

### 小结

当前代码已经足以支撑“轻编排式会话控制 + 迭代式 ML 求解”这个组合，但企业如果想要真正的交互式 ML 平台，还需要一层更偏业务持久化与执行治理的重编排把两者连起来。

## 3. 交互式 ML 自动化应该怎么接

### 3.1 推荐的总体思路

最稳妥的方式，不是让 ACP 直接替代 `autogluon-assistant` 去求解，也不是让 `autogluon-assistant` 继续只接受一次性任务，而是把完整请求拆成几个清晰阶段：先讨论，再锁定，再执行，再优化。ACP 承载这些阶段之间的会话、轻量意图识别、阶段判断、命令、计划和状态流；`autogluon-assistant` 在执行与优化阶段负责真正的数据理解、代码生成、训练运行与持续试错；中间再加一层更偏业务持久化和执行控制的重编排，把多轮自然语言逐步沉淀成结构化任务定义。

这种思路的最大好处，是它把“训练代码质量”问题前移到了“任务定义质量”问题。真实环境里，训练失败很多时候不是因为模型不会写 `fit()`，而是因为系统根本没先搞清楚目标列、评价指标、资源限制和字段处理原则。只要能把这些关键信息先在会话里讨论清楚，再进入求解阶段，后面的代码质量和训练策略命中率就会明显提升。换句话说，ACP 提升的不是底层模型智商，而是整个求解过程的对齐程度。

### 3.2 训练阶段为什么不能只剩日志

一旦进入执行阶段，ACP 的主动性不应该退化成一个日志转发器。更合理的方式，是让 `autogluon-assistant` 的关键内部状态持续映射为 ACP 事件流，并配合命令公开和计划回传，让用户随时知道当前进展和下一步空间。例如，开始一轮新迭代时可以回传阶段说明；选定了哪条工具链时可以回传策略说明；代码执行开始和结束时可以映射成 `tool_call`/`tool_call_update`；分数变化和最佳结果刷新时可以回传结果摘要；当会话进入某个明确阶段时，还可以通过 `available_commands_update` 显式公开“继续优化”“只保留 tabular 路径”“切换到更节省算力的模式”“从当前结果分叉实验”之类的动作。

这种设计的价值，在于它把训练过程从“散乱日志”变成“可理解的求解会话流”。对于业务用户和平台前端来说，这两者差别很大。日志只说明程序发生了什么，会话流则同时说明系统现在在做什么、为什么这么做、下一步还能做什么。ACP 当前已经具备承载这类主动控制信息的结构，所以设计时不应再把它压缩回普通消息壳。

### 3.3 轮间修改应该怎么做

第一版方案里，最现实也最有价值的目标，是把用户修改点稳定插入到“轮与轮之间”。例如，用户在某一轮之后提出“不要再尝试多模态，只做表格任务”“指标改成 F1”“训练时间最多 15 分钟”“忽略某个异常文本字段”，这些指令不需要新建任务，也不需要回到起点重来，而应该继续进入当前 session。编排层将其整理为新的约束条件，影响下一轮 `NodeManager.step()` 之前的上下文、工具选择和代码生成。

基于代码现状，这样的能力是有现实抓手的。`NodeManager` 在每轮生成代码前都会重新获取当前步输入，WebUI/MCP 侧也有等待输入与继续注入的机制。因此，ACP 完全可以先承担前半段轻编排职责，例如识别这是一条“轮间修正”而不是新的独立任务，判断它应影响当前会话的后续阶段，并通过计划和命令更新把影响范围先公开出来；而重编排层再把这条新增要求沉淀成“当前 session 的后续约束”，并在下一轮开始前送给求解器。需要避免的是把文档写成“训练一旦开始，用户就能实时打断正在运行的单轮训练并立刻重写其内部逻辑”。那不符合当前实现边界，也没必要在第一版里承诺。

### 小结

`ACP + autogluon-assistant` 的真正价值，不是让训练看起来像聊天，而是让机器学习自动化第一次有了“先讨论、再锁定、后执行、可轮间纠偏、能持续优化”的完整协作闭环。

## 4. 企业交互式 ML 平台的总体架构

### 4.1 分层设计

建议把系统拆成五层：

| 层级 | 作用 | 关键组件 |
|---|---|---|
| 接入层 | 承接 Web、IDE、企业门户、数据上传与结果查看 | Web App、ACP Client、文件上传入口 |
| 会话控制层 | 统一承载会话、轻量意图识别、命令、计划、权限和状态流 | ACP、业务会话映射表 |
| 编排层 | 负责重编排、任务沉淀、状态持久化与执行翻译 | ML Session Orchestrator、Task Spec Builder |
| 求解层 | 负责 AutoML 求解与持续优化 | `autogluon-assistant`、`NodeManager`、各类 agents |
| 治理层 | 负责状态、产物、审计、执行隔离和资源治理 | Task Store、Artifact Store、Runner、Audit Log |

### 4.2 各层职责边界

这里最需要强调的是会话控制层、编排层和求解层之间的边界。会话控制层并不负责具体训练逻辑，但它不应只是被动转发层，而应该承担会话级的轻编排职责，例如识别当前输入属于讨论、确认、轮间修正还是继续优化，判断当前阶段，并公开当前可用命令、模式、配置项与计划项。求解层也不应该负责企业会话语义，它要做的是“在给定约束下持续尝试、评估和优化模型与代码”。而编排层则继续承担更重的业务职责：把多轮自然语言沉淀成结构化任务定义，把后续约束持久化，把运行状态和结果索引稳定落库，并把求解状态翻译成用户能理解的会话流。

因此，平台设计时不应该把所有编排逻辑都硬塞进 ACP，也不应该让 `autogluon-assistant` 直接承担所有业务状态机。更稳妥的做法，是把 ACP 提升为“轻编排与会话控制层”，把 `autogluon-assistant` 当成“求解器”，再用专门的 Orchestrator 负责重编排、持久化与执行治理。这样每一层的复杂度都可控，后续替换底层模型、扩展任务类型或接入新前端时也更稳。

### 4.3 端到端流程

一次典型的交互式 ML 自动化请求，建议这样流转：

1. 用户在前端或 IDE 中创建新的 ML 会话，并上传数据目录或样本文件。
2. 系统通过 ACP 创建 session，并保存业务会话与 ACP session 的映射。
3. ACP 先做会话级阶段判断与输入归类，编排层再调用数据理解能力，生成数据画像和任务候选判断。
4. 会话进入讨论阶段，补齐目标列、问题类型、评价指标、资源预算与字段约束。
5. ACP 先公开当前确认动作与计划，编排层再整理出结构化任务草案让用户确认。
6. 用户确认后，系统调用 `autogluon-assistant` 进入正式求解。
7. 求解过程中，关键迭代状态、工具执行状态、分数变化和最佳结果更新持续回传到当前会话。
8. 用户可以在轮与轮之间继续追加约束，影响后续求解；也可以基于当前结果分叉实验路径。
9. 最终产物、日志和评估结果统一归档，并绑定到当前业务会话。

### 小结

这个架构的组织方式不应该围绕“调哪个模型”来设计，而应该围绕“会话、控制、任务、求解、治理”来设计。ACP 和 `autogluon-assistant` 在其中各自承担一块非常清晰的职责。

## 5. 为什么这种组合能提高训练代码质量

### 5.1 提升不来自协议本身，而来自过程完整性

这个方案确实会提高最终生成训练代码和训练流程的质量，但提升方式不是“换了 ACP 之后模型突然更聪明了”，而是“整个任务定义和求解过程变完整了”。很多训练代码表面上写得没错，实际效果却差，原因往往不是语法问题，而是目标列确认错了、评价指标理解错了、资源限制没体现、某些字段本来就该排除、业务其实只接受某一种求解路径。只要这些问题没有在训练前说清楚，后面即使自动生成了很多代码，也只是在偏掉的方向上越跑越远。

引入 ACP 之后，系统第一次可以比较自然地把“讨论任务定义”和“执行求解”拆开。用户先把目标和边界讲清楚，系统再把这些边界固化进后续求解过程里；执行过程中如果出现偏航，还可以在轮间插入新的要求继续校正。`autogluon-assistant` 则继续发挥它的数据理解、工具选择、试错和优化能力。最终提升的，是交付代码的命中率、可运行性和贴题程度，而不是某个单点 prompt 的华丽程度。

### 5.2 `autogluon-assistant` 为什么仍然不可替代

即使有了 ACP，也不能把 `autogluon-assistant` 看成一个可随时替换掉的薄壳。它真正不可替代的地方在于，它已经把机器学习自动化做成了专业求解器，而不是普通代码助手。它知道怎么先理解数据，再选择工具，再生成和执行代码，再根据验证结果继续改进。这意味着平台最终交付的不是一份静态训练模板，而是一条会围绕验证反馈持续优化的求解轨迹。

如果只保留 ACP，再接一个通用 coding agent，当然也可以生成训练脚本，但那更像一个“会写代码的助手”，而不是一个“会围绕 AutoML 目标持续求解的系统”。对于企业内部平台来说，两者价值差距很大。前者更适合临时性技术辅助，后者才更接近业务可复用的自动化能力。

### 小结

这个方案提高训练代码质量的关键，不是给现有模型换一个外壳，而是让机器学习自动化拥有了更完整的任务对齐和求解闭环。ACP 让交互更强，`autogluon-assistant` 让求解更专业。

## 6. 落地建议

### 6.1 第一阶段先验证什么

第一版不建议一上来就做完整企业 ML 平台。更实际的目标，是先验证三件事：第一，用户能否在同一个 session 里先讨论再执行；第二，求解过程能否被稳定翻译成 ACP 会话流，而不是只能看散乱日志；第三，用户在每轮之间补充约束之后，后续求解路径是否真的会跟着变化。只要这三件事成立，这套方案就已经有非常明显的业务价值。

建议 MVP 先控制在：

- 单用户或受控试点租户
- 单机 Runner 或有限执行节点
- 以表格任务为主
- 支持讨论、确认、执行、继续优化
- 支持结果归档与基于结果继续迭代

### 6.2 第二阶段再补什么

| 能力 | 为什么适合后置 |
|---|---|
| 多任务类型扩展 | 先把 tabular 跑稳，再扩时序和多模态 |
| 分叉实验治理 | 第一版先把单路径继续优化做顺 |
| 容器化与强隔离执行 | 依赖基础设施改造与资源治理 |
| 多用户并发与任务队列 | 需要状态存储、调度和资源管理成熟 |
| 成本、审计与配额治理 | 需要完整元数据和事件体系支持 |

### 6.3 最终建议

比较合理的实施路径是：

1. 用 ACP 做统一会话、轻编排与主动控制入口。
2. 增加一个轻量的 ML Session Orchestrator 负责重编排与业务持久化控制。
3. 保留 `autogluon-assistant` 作为 ML 自动化求解内核。
4. 用独立 Runner 或容器承载训练执行。
5. 用业务侧状态存储和产物存储承接会话、日志和结果。

### 小结

这不是一个“把训练脚本接到聊天框里”的项目，而是一条可以持续对齐需求、逐轮优化结果的交互式 ML 生产链。只要边界切得清楚，它完全有机会演进成企业内部可用的 ML 自动化平台。
