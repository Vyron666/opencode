# runtime-shell 架构规范

补充文档：

1. `docs/ENTERPRISE-ROADMAP-P1-P3.md`：定义 `P1 / P2 / P3` 的企业化改造方案与分阶段实施口径。

本文档定义 `runtime-shell` 的企业级架构基线，用于指导当前代码收敛与后续企业化演进。目标不是一次性补齐所有平台能力，而是确保系统在继续演进时具备清晰分层、可治理边界、稳定运行面与可运维基础。

## 1. 架构目标

`runtime-shell` 必须从“本地可跑的原型”演进为“可治理、可隔离、可审计、可扩展、可运维”的运行平台。

当前阶段的目标：

1. 明确分层职责，避免路由、运行时、持久化逻辑交叉污染。
2. 明确目录结构，保证新代码有稳定落点。
3. 明确访问边界，所有会话、工作区、配置访问必须可在服务端校验。
4. 明确运行时治理边界，为后续 Worker 调度、数据库持久化、RBAC、审计增强预留结构。
5. 明确运维基线，包括日志、审计、健康检查、配置变更、发布回滚与测试口径。

## 2. 核心原则

1. HTTP 路由只负责鉴权入口、入参校验、调用应用服务、返回响应。
2. 应用服务负责业务编排、访问校验、审计触发、运行时调用。
3. Repo 只负责数据访问，不承载权限规则与业务决策。
4. Runtime/ACP 只负责会话运行时生命周期、事件桥接与交互，不负责租户权限判断。
5. 所有可见性边界必须在服务端执行，前端参数不构成授权依据。
6. 工作区只能使用已登记的绑定记录，不能接受任意路径直接执行。
7. 配置变更必须具备影响范围与审计记录。
8. 关键链路必须能记录 `requestId`、`userId`、`tenantId`、核心业务 ID。

## 3. 目录规范

当前服务端目录应按以下职责长期收敛：

```text
server/src
├─ acp/                         # ACP 进程、协议、桥接客户端
├─ http/
│  ├─ routes/                   # 薄路由，只做协议层职责
│  ├─ response.ts               # 统一响应结构
│  ├─ schemas.ts                # HTTP 入参校验
│  └─ *-support.ts              # 仅保留 HTTP 适配类 support
├─ repos/                       # 纯数据访问层
├─ runtime/                     # 运行时注册、事件分发、会话绑定
├─ services/
│  ├─ auth/                     # 认证、用户上下文、脱敏输出
│  ├─ access/                   # RBAC、资源动作校验、范围授权
│  ├─ session/                  # 会话访问校验、会话应用服务、摘要、事件构造
│  ├─ workspace/                # 工作区绑定与路径边界校验
│  ├─ worker/                   # Worker 注册、心跳、状态管理
│  ├─ scheduler/                # 新会话调度、粘性路由
│  ├─ settings/                 # 配置与模型管理应用服务
│  ├─ configuration/            # 分级配置读取、合并、快照解析
│  ├─ config-impact/            # 配置变更影响范围分析
│  ├─ config-approval/          # 配置审批编排
│  ├─ extension-policy/         # MCP / skill / provider 启用策略
│  ├─ system/                   # Worker、健康检查、系统视图服务
│  ├─ runtime/                  # 运行时编排应用服务
│  └─ runtime-governance/       # runtime 生命周期、恢复、回收
├─ store/                       # 当前阶段的内存/JSON 持久化实现
└─ types.ts                     # 领域类型定义
```

禁止：

1. 在 `http/routes` 中直接编写复杂业务编排。
2. 在 `repos` 中写权限判断、租户边界逻辑。
3. 在 `runtime` 中直接写用户可见范围判断。
4. 在多个目录重复定义同一种访问规则。

## 4. 分层职责

### 4.1 HTTP 层

负责：

1. 鉴权入口。
2. 请求参数校验。
3. 调用应用服务。
4. 将服务返回映射到统一 HTTP 响应。

不负责：

1. 工作区合法性判断细节。
2. 会话生命周期编排。
3. 配置变更后的会话重载策略。
4. 审计内容拼装细节。

### 4.2 应用服务层

负责：

1. 业务编排。
2. 会话访问校验。
3. 工作区边界校验。
4. 审计触发。
5. 配置变更影响处理。
6. Worker 与运行时调用编排。

要求：

1. 每个服务模块面向一个稳定领域能力。
2. 返回显式结果，不依赖路由层猜测失败原因。
3. 关键约束需要中文/English 注释说明。

### 4.3 Repo 层

负责：

1. CRUD。
2. 排序、过滤、分页。
3. 幂等唯一键落点。
4. 后续数据库事务边界。

不负责：

1. 用户是否有权访问某资源。
2. 配置变更是否允许重载会话。
3. Worker 选择策略。

### 4.4 Runtime 层

负责：

1. ACP 进程生命周期。
2. Session 与 ACP session 绑定。
3. 上游事件转发。
4. Pending permission/question 注册与回调。

不负责：

1. 租户/组织/项目访问控制。
2. 任意路径 workspace 接受策略。

## 5. 认证、权限与隔离

当前基线：

1. 所有用户请求必须从服务端 session 中恢复用户。
2. 会话、工作区、配置访问都必须至少按 `tenantId + organizationId` 过滤。
3. 创建会话时必须校验 `workspaceId + projectId + user scope`。
4. 事件流订阅必须先做会话访问校验。

后续企业化要求：

1. 引入持久化认证会话。
2. 引入 RBAC 与资源范围授权。
3. 引入项目级与工作区级可见性控制。

## 6. 工作区边界

1. 前端不得直接提交任意 `workspacePath` 用于执行。
2. 运行时只允许使用已登记 `workspace` 的 `rootPath`。
3. 工作区校验必须发生在应用服务层，而不是 ACP 层。
4. 工作区非法、越权、不存在必须有明确区分错误。

## 7. 运行时与 Worker 治理

当前基线：

1. 所有 session runtime 操作必须通过统一编排入口触发。
2. 运行时事件发布与会话事件构造必须收敛，不允许路由自己拼事件。
3. Worker 状态更新不应散落在多个路由中。

后续企业化要求：

1. Worker 注册、心跳、容量、负载治理。
2. Session 与 Worker 粘性绑定。
3. 僵尸 runtime 回收、超时、失败恢复。

## 8. 配置治理

当前基线：

1. Provider 配置与 custom models 修改必须走应用服务。
2. 配置变更需要产生审计记录。
3. 配置变更影响当前 session 时，重载策略必须由服务层统一执行。

后续企业化要求：

1. 平台级、租户级、项目级、工作区级、会话级配置分层。
2. MCP/skill/provider 启用策略与审批策略。

## 9. 审计、安全与可观测性

最低要求：

1. 写操作必须记录 `requestId`、`userId`、资源 ID、动作类型。
2. 日志不能输出密码、token 原文、密钥。
3. 统一响应结构使用 `code/message/data/requestId`。
4. 健康检查与 Worker 视图必须有稳定入口。

后续要求：

1. 结构化日志。
2. traceId/requestId 全链路透传。
3. 指标、告警、限流、防重放与敏感字段脱敏。

## 10. 持久化与发布演进

当前阶段允许 `store/` 作为过渡实现，但必须满足：

1. HTTP 与服务层不能耦合 JSON 文件细节。
2. Repo 接口必须是未来切 DB 的唯一切换点。
3. 不允许在新代码中继续扩大路由对 `store` 的直接业务耦合。

后续目标：

1. 引入正式数据库层与 migration。
2. 认证会话、workspace、business session、worker、audit 全量持久化。
3. 支持灰度、回滚与配置变更流程。

## 11. 测试与验收

每轮架构调整至少满足：

1. `bun run typecheck` 通过。
2. 路由文件业务复杂度下降，应用服务职责上升。
3. 相同校验逻辑不再在多个路由重复实现。
4. 关键代码具备中文/English 注释说明约束。

建议后续补齐：

1. service 单测。
2. 会话创建/打开/恢复/取消集成测试。
3. 多租户越权访问测试。
4. Worker 故障与配置错误演练。

## 12. 当前代码对齐要求

本轮及后续几轮重构，应优先对齐以下事项：

1. `session-core-routes.ts` 的会话创建、详情、关闭、打开继续收敛到应用服务。
2. `acp-session-routes.ts` 的 load/resume/fork/input/cancel/config 更新继续向会话运行时应用服务收敛。
3. `session-settings-routes.ts` 的 custom models/provider save 收敛到 `services/settings`。
4. `system-routes.ts` 的 worker health 聚合收敛到 `services/system`。
5. `store-service.ts` 后续拆解为更明确的领域 store/repo 门面，避免继续膨胀。

## 13. 文档生效规则

1. 新增代码必须优先遵循本文档的目录与职责边界。
2. 若现有代码与本文档冲突，优先通过小步重构向本文档靠拢。
3. 若需要偏离本文档，必须在改动说明中明确偏离原因与回收计划。
